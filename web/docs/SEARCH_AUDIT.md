# Аудит поиска по вакансиям

Дата: 2026-08-09. База на момент замеров: 531 опубликованная неархивная вакансия.
Прод-схема: `NEXT_PUBLIC_VACANCIES_SCHEMA=root`.

## 1. Как поиск работает сейчас

Точка входа: `app/vacancies/page.tsx:71` -> `listVacancies()` -> `lib/data/vacancies.ts:208-218`.

```ts
const term = `%${escapeIlikeTerm(needle)}%`;
q.or(`title.ilike.${term},company.ilike.${term},description.ilike.${term}`)
```

Это всё. Один подстрочный `ILIKE` по трём полям, склеенный через `OR`.

Порядок выдачи задаётся до и независимо от запроса:

```ts
.order("is_featured", { ascending: false })
.order("published_at", { ascending: false })
```

а затем результат ещё раз перемешивается `diversifyVacanciesByCompany()`
(`lib/data/vacancies.ts:140`), которая раскидывает вакансии одной компании по
всему списку. То есть **релевантности в выдаче нет вообще ни на одном шаге**.

Отдельно: колонка `search_vector tsvector` объявлена в
`supabase/migrations/20260419000000_initial_careerlab_schema.sql:25` как
generated + GIN-индекс `vacancies_search_vector_idx`. В проде колонка есть,
но **значения `NULL`** (проверено через REST: `select=search_vector` отдаёт
`null`, `search_vector=fts(russian).python` отдаёт `[]`). Генерируемое
выражение потеряно при одной из последующих миграций. Индекс мёртвый,
инфраструктура FTS оплачена, но не используется.

## 3. Пять корневых причин

### 3.1 Поиск по полному тексту описания без ранжирования

`description` у парсерных вакансий это 2-5 КБ текста со стеком, требованиями и
блоком «будет плюсом». Любое упоминание слова там весит столько же, сколько
слово в заголовке. При 531 вакансии «sql» встречается в описании у трети базы.

### 3.2 Многословный запрос ломается

`ILIKE '%python разработчик%'` требует буквального соседства слов в этом порядке.

| Запрос | Результатов сейчас |
|---|---|
| python | 160 |
| python разработчик | **1** |
| разработчик python | **0** |
| junior python | 3 |

Пользователь, уточняющий запрос, получает пустую страницу. Это худший из
возможных сигналов: система наказывает за более точную формулировку.

### 3.3 Подстрока без границ слова

`%java%` матчит `JavaScript`. Из 22 «java»-заголовков четыре это JavaScript и
QA Auto JavaScript. То же самое с `%го%`, `%1с%`, `%ml%` и любым коротким
токеном: `ml` найдётся внутри «HTML», «Excel-модель» и десятка русских слов.

### 3.4 Нет морфологии, синонимов и раскладки

- «фронтенд» -> 7 результатов, «frontend» -> 14. Разные множества, пересечение неполное.
- «тестировщик» -> 12, «QA» -> 24, «тестирование» -> 65. Три запроса про одно и то же.
- Стемминга нет: «продажи» / «продаж» / «продажник» это три разных поиска.
- Раскладка: `pbnhjy` (питон вслепую) -> 0 результатов, без подсказки.
- Опечатки: «аналитк» -> 0.

### 3.5 Спецсимволы в запросе портят фильтр

`escapeIlikeTerm()` (`lib/data/vacancies.ts:38`) экранирует только `%`, `_` и `,`.
Скобка в запросе рвёт синтаксис PostgREST-группы `or=(...)`:
`q=python)` возвращает 2 результата вместо 160, `q=1c (ERP)` возвращает 0.
Ошибку код глотает и отдаёт пустой список (`lib/data/vacancies.ts:224-230`).

## 4. Смежные дефекты, найденные попутно

1. **`diversifyVacanciesByCompany` применяется и к поисковой выдаче**
   (`app/vacancies/page.tsx:51`). Даже если появится ранжирование, эта функция
   его затрёт. Её нужно применять только к дефолтному листингу без `q`.
2. **Счётчики фасетов не зависят от запроса и вообще не выводятся.**
   `listVacancyFilterOptions()` вызывает `listVacancies({limit:1000})` без
   фильтров, то есть считает по всей базе. При этом `VacancyFilterForm` рисует
   только подпись опции: посчитанный `count` в разметку не попадал. Фильтр
   выбирался вслепую, без понимания, сколько за ним вакансий.
3. **Нет пагинации.** Запрос без `limit` тянет все 531 строки на каждый заход.
4. **`skills[]` заполнен у 33 вакансий из 531** - только у Яндекса (20) и ДРТ (8).
   У Т-Банка, Сбера, Альфы, Ozon (357 вакансий на четверых) пустой. Поле даёт
   самый точный сигнал по стеку, парсеру стоит его заполнять для всех источников.
5. **Нет лога запросов.** Не видно, что ищут и что даёт ноль результатов, то есть
   улучшать поиск сейчас можно только вслепую.
6. **В базе знаний та же проблема** (`lib/data/articles.ts:44`): `ilike` по
   `title` и `excerpt`, тело статьи не ищется вообще.

## 5. Что делать: целевая архитектура

При 531 документе внешний поисковый движок (Elasticsearch, Typesense, Meilisearch)
не нужен и не окупается. Postgres full-text search закрывает задачу целиком, а
инфраструктура под него в схеме уже заложена. Проверено на живой базе: русский
словарь работает, `websearch_to_tsquery` доступен через PostgREST.

### Слой 1. Нормализация запроса (в приложении)

Перед походом в базу:
- тримминг, схлопывание пробелов, нижний регистр;
- **исправление раскладки**: если запрос целиком в кириллице и не даёт результата,
  прогнать через таблицу ЙЦУКЕН -> QWERTY и повторить;
- **словарь алиасов** (30-50 пар, обычный TS-объект, без БД):
  `фронтенд|фронт -> frontend`, `бэкенд -> backend`, `тестировщик|тестирование -> qa`,
  `питон -> python`, `джава -> java`, `аналитик данных -> data analyst`,
  `продакт -> product manager`, `1с -> 1c`. Алиас **добавляется** к запросу через
  `OR`, а не заменяет его.

### Слой 2. Матчинг: tsquery вместо ILIKE

Восстановить `search_vector` как generated-колонку с весами:

```sql
setweight(to_tsvector('russian', coalesce(title,'')), 'A')
|| setweight(to_tsvector('russian', coalesce(company,'')), 'B')
|| setweight(to_tsvector('russian', array_to_string(skills,' ')), 'B')
|| setweight(to_tsvector('russian', coalesce(description,'')), 'C')
```

Матчинг через `websearch_to_tsquery('russian', q)`. Это сразу решает 3.2, 3.3, 3.4
и половину 3.5:

| Запрос | ILIKE по title | FTS по title |
|---|---|---|
| java | 22 (с JavaScript) | **18** (JavaScript отсеян) |
| python разработчик | 1 | **9** |
| разработчик python | 0 | **9** (порядок слов не важен) |
| аналитик | 108 | 107 (морфология: аналитику, аналитика) |

`websearch_to_tsquery` заодно бесплатно даёт синтаксис `"точная фраза"` и `-минус слово`
и не падает на скобках и кавычках.

Для живого автодополнения к последнему слову запроса добавлять `:*` (префиксный поиск).

### Слой 3. Ранжирование и двухуровневая выдача

Это ключевая часть для «без левых». Одного FTS мало: по «python» всё равно найдётся
160 вакансий, где слово есть в описании. Разница в том, что теперь их можно
**упорядочить и разделить**.

Скоринг:

```
score = ts_rank_cd('{0.1, 0.2, 0.4, 1.0}', search_vector, query)
      * (1 + 1.5 * точное вхождение запроса в title)
      * (1 + 0.3 * свежесть: published_at за последние 14 дней)
      * (1 + 0.5 * featured)
```

Выдача делится на две группы, как на hh:
- **Основная** - совпадение в `title` / `company` / `skills` (вес A и B). Для «python»
  это те самые 16.
- **«Ещё 144 вакансии упоминают Python в описании»** - свёрнутый блок ниже
  разделителя. Не выбрасываем (там реально бывают релевантные), но не выдаём за
  результат поиска.

Плюс тумблер «искать только в названии» в фильтрах, как отдельный явный контроль.

Реализация: одна SQL-функция `search_vacancies(q, filters..., limit, offset)`,
вызывается через `supabase.rpc()`. Фильтры (сфера, город, опыт, формат, зарплата)
применяются внутри неё же, чтобы ранжировать уже отфильтрованное множество.

### Слой 4. Фолбэк на опечатки

`pg_trgm` + `similarity(title, q) > 0.3`, GIN-индекс `gin_trgm_ops` на `title`.
Запускается **только если основной запрос дал 0 результатов**: «аналитк» ->
«аналитик». Показывать как «Возможно, вы имели в виду: аналитик».

### Слой 5. Наблюдаемость

Таблица `search_queries (q, results_count, filters, created_at)`, запись асинхронно.
Без неё нельзя ответить на вопрос «стало ли лучше». Первый отчёт, который нужен:
топ запросов с нулём результатов - это готовый список дырок в словаре алиасов.

## 7. Что сделано в этапах 1-2

Миграция `web/supabase/migrations/20260809000000_vacancy_search.sql`, применена
на проде ролью `supabase_admin`:

- `search_vector` пересоздана как generated с весами A=title, B=company/city/skills,
  C=description; заполнена по всем 1456 строкам таблицы;
- GIN-индекс `vacancies_search_vector_idx` + пропущенные в проде
  `vacancies_published_at_desc_idx` и `vacancies_filters_idx`;
- функция `public.search_vacancies(...)` (security invoker, RLS работает как
  раньше), grant на `anon`;
- `public.immutable_array_to_string()` - обёртка, потому что штатный
  `array_to_string` помечен STABLE и generated-колонку с ним создать нельзя
  (первая попытка миграции упала на `generation expression is not immutable`).

Приложение:

- `lib/data/vacancies.ts` - при непустом `q` идёт в RPC; если функции нет
  (PGRST202), молча падает обратно на прежний ILIKE, поэтому окружения без
  миграции продолжают работать;
- `app/vacancies/page.tsx` - `diversifyVacanciesByCompany()` больше не
  применяется к поисковой выдаче (иначе перемешивала ранжирование);
  результат делится на основную выдачу и свёрнутый блок
  «Ещё N вакансий упоминают «q» в описании»; полоса «Рекомендуем» при поиске
  скрыта, буст за закрепление учтён внутри score;
- отдельный текст пустой выдачи для поиска и для случая «в названиях нет,
  но в описаниях есть».

## 8. Что сделано в этапах 3-5

Миграции `20260809120000_vacancy_search_phase2.sql` (роль supabase_admin) и
`20260809120100_search_queries.sql` (роль приложения), обе применены на проде.

**Этап 3, нормализация запроса** - `lib/search/query.ts`:

- словарь из 28 групп взаимозаменяемых терминов (frontend / фронтенд / фронт,
  qa / тестировщик / тестирование, developer / разработчик / программист, ...);
- исправление раскладки в обе стороны: «знерщт» -> «python», «gbnjy» -> «питон»;
- варианты не заменяют запрос, а добавляются к нему: в SQL они склеиваются
  через OR (`combine_tsqueries`), поэтому расширение может только добавить
  находки. Максимум 6 альтернатив, раскладка добирается последней.

Намеренно не включены короткие двусмысленные токены (go, ds, ts, ui) и
морфология - её уже закрывает русский словарь в `to_tsvector`.

**Этап 4, фасеты**:

- `vacancy_facets()` считает каждое измерение с учётом всех остальных
  (drill-down) и только по основной выдаче (`match_tier <= 1`), то есть счётчик
  равен тому, что пользователь получит после клика. Проверено: при `q=python`
  фасет «IT 24», клик по нему даёт ровно 24;
- счётчики наконец выводятся в панели фильтров; значения без совпадений
  показываются нулём и приглушаются;
- совпадения только в описании - свёрнутый блок `<details>` внизу выдачи.

**Пагинация: сделана и откатана.** Разбивка по 20 с отдельным экраном
`?in=description` для упоминаний работала, но бесконечный листинг на
`/vacancies` - осознанное продуктовое решение, а не следствие недосмотра.
Параметры `page`/`per_page`/`only_tier` в `search_vacancies()` остались, страница
зовёт функцию с `per_page = 1000` и отдаёт всё разом. Рассеивание по компаниям
при этом осталось в SQL (`row_number()` по компании): результат тот же, что у
прежней `diversifyVacanciesByCompany()`, но одним запросом.

**Этап 5, опечатки и лог**:

- `search_vacancies_fuzzy()` на триграммах, порог `similarity > 0.25`.
  Вызывается только при нуле точных совпадений: «аналитк» -> «Аналитик»,
  «Аналитик данных», «Бизнес-аналитик»;
- таблица `search_queries` + запись из `after()`, чтобы лог не задерживал
  ответ. Ошибка записи проглатывается: упавший лог не роняет выдачу.

## 9. Остаточные риски

- `search_vector` пересчитывается на каждом UPDATE парсера. При 1456 строках и
  максимум 5.5 КБ описания это незаметно, но за временем прогона парсера стоит
  последить.
- Кеш страницы `unstable_cache` 120 секунд: после правки ранжирования или
  словаря алиасов эффект виден не сразу.
- Словарь алиасов ручной. Развивать его нужно по отчёту из `search_queries`
  (запросы с `results_count = 0`), а не по догадкам.
- Фасеты считаются по основной выдаче: цифры в панели фильтров не учитывают
  свёрнутый блок с упоминаниями в описании.
- Пагинации нет по продуктовому решению, поэтому страница по-прежнему отдаёт
  всю выдачу разом (557 карточек). Тяжёлые поля из карточек вычищаются, но при
  заметном росте базы за весом ответа стоит следить.
- `skills[]` заполнен у 6% вакансий. Это самый точный сигнал по стеку, и он
  уже участвует в поиске - заполнение поля в парсере даст заметный прирост
  точности без единой правки в поиске.
